# YikaiCMS 结构质量评审

**只评审，不动手。** 输出结论和依据，改不改由用户决定。

## 分工（先确认你该不该在这儿）

| 想干的事 | 用哪个 |
|---|---|
| 找 bug、正确性 | `/code-review`（带验证，会标 CONFIRMED/PLAUSIBLE） |
| 小范围清理并**直接改** | `/simplify` |
| 并 main 前的红线闸门 | `yikai-precheck` |
| **结构够不够好、抽象值不值、要不要重做** | **本 skill** |

和 `/simplify` 的区别：那个是局部清理且会落刀；这个只看**结构高度**——层级、边界、概念数量，且只出报告。
两个都不负责正确性；正确性是 `premerge-check` 的事。

## 硬规则（可证伪，先跑数据再说话）

### 1. 文件行数棘轮

```bash
git diff --stat main...HEAD                       # 本轮改了哪些文件
wc -l <改动文件>                                   # 改后行数
git show main:<文件> | wc -l                       # 改前行数
```

| 情况 | 判定 |
|---|---|
| 从 <600 涨到 >600 | **推定阻断**，先问能不能拆 |
| 本来就 >600，本轮又变大 | **推定阻断**（棘轮：已超标的只准变小） |
| 本来就 >600，本轮变小或持平 | 通过 |

由来：本仓 796 个 PHP 文件，中位数 **106 行**，P90 **435**，P95 **646**。
直接抄 Cursor 那份的 1000 行阈值在这里几乎永不触发（全仓只有 23 个文件过 1000）。
600 是按本仓真实分布定的。

**豁免（数据不是逻辑，行数无意义）**：
`lang/*.php`、`plugins/logo-maker/assets/icon-library/icons-index.php`、
数据库迁移、生成产物、`assets/css/tailwind.css`。
**不豁免**已知的大逻辑文件——`admin/blox_editor.php`(8337)、`includes/functions.php`(3672)、
`admin/blox_editor/partials/workspace.php`(3100)、`admin/page_edit_advance.php`(2823)
就是当前的结构债，它们适用棘轮：可以不拆，但不许再涨。

### 2. 删除 > 搬运

重构的记分口径是**概念数量**，不是「代码动了多少」。每条重构建议必须能回答：

- 读者需要同时装在脑子里的概念，是少了还是只是换了地方？
- 净删除多少行？只搬不删的重构，默认不值得做。

看到「能整层删掉」的路径，优先推那条，而不是把同样的复杂度重新排列一遍。

### 3. 建议规模与 diff 成比例

**这是 Cursor 原版缺的一条，也是它最容易失控的地方。**

| 本轮 diff | 允许提的最大建议 |
|---|---|
| < 50 行 | 只提本轮引入的问题；历史债写进「另立一轮」 |
| 50–500 行 | 可提被改动文件内部的重构 |
| > 500 行 / 明确说了是重构轮 | 可提跨文件、跨层的结构调整 |

对着一个 20 行的 bugfix 要求重构整个模块——这不是严格，是评审失控。
路线图 §8 已明确暂缓大改（不做 Vue/React 重写、不做自由画布），本 skill 不得越过那条线。

## 判断项（软的，靠证据不靠语气）

1. **散乱分支** —— 新增的 `if` 是不是插进了和本功能无关的既有流程？是就当设计问题，不是风格问题。
2. **薄包装** —— 只是转发一层、没有收敛任何东西的 helper／wrapper，删掉更清楚。
3. **逻辑放错层** —— 功能逻辑漏进公共路径，或实现细节漏出 API。本仓的层次是
   `includes/`（领域） → `includes/builder/`（Blox） → `admin/`（页面） → `plugins/`（插件）。
4. **边界不显式** —— PHP 这边看的是 Psalm 契约，不是 TS 的 `any`/`unknown`：
   靠 `?string` 兜底、靠静默 fallback 掩盖不清楚的不变式、`@psalm-suppress` 新增豁免，都要问一句
   「边界是不是本来就该写明」。**新增独立入口别忘了 `psalm.xml` 的 `MissingFile` 豁免**（见 `yikai-precheck` 判断二）。
5. **重复造轮子** —— 声称「已有 canonical helper」时必须给出真实路径行号，见下。

## 收尾验证（不做完不许出结论）

**Cursor 原版完全没有这一步，所以它会自信地建议不存在的重构。** 本 skill 必须做：

- [ ] 每条「已有现成 helper 可复用」——给出 `文件:行号`，且真的 `grep` 过；找不到就降级成猜测或删掉
- [ ] 每条「行为不变」——指出**哪个测试**覆盖了它；没有测试覆盖的，明确写「行为等价未经验证」
- [ ] 每条行数判定——附改前/改后真实数字，不许估
- [ ] 拿不准的写「待确认」，**不要为了语气强硬而把猜测说成结论**

## 输出

按此优先级，**只留高置信的少数几条**，宁缺毋滥：

1. 结构性倒退（本轮把结构改差了）
2. 错过的整层简化机会
3. 分支复杂度增长
4. 边界／抽象／契约问题
5. 文件体积与拆分
6. 可读性

每条给：`文件:行号` → 问题 → 建议 → 证据（测试名／helper 路径／行数）。
**不要凑数**。没有结构问题就直说没有——这比编三条凑格式有用。

## 不适用

hotfix、生成代码、`vendor/`、数据库迁移、`lang/*.php`、纯文案改动、
以及用户已经说明「这轮先不管结构」的时候。
